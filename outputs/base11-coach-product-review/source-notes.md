## 실제 화면 확인

로컬 코치 웹에서 다음 화면의 정보 구조와 상호작용을 직접 확인했다.

- 마이크로사이클 대시보드
- 월간 일정
- 훈련 세션 상세
- 선수별 컨디션·참여·RPE·퀵 피드백
- 팀 개요·스태프·설정

화면은 시각적으로 일관되고, 예외 우선과 세션 중심이라는 제품 원칙이 잘 드러난다. 그러나 화면의 다수 수치와 상태는 프리뷰 데이터이며, 일정 생성·수정과 일부 선수 입력은 서버가 아니라 브라우저 로컬 저장소에 저장된다.

## 검증 결과

- 코치 웹 프로덕션 빌드: 통과, 16개 앱 라우트 생성
- API 테스트: 20개 통과
- API 린트·포맷 검사: 통과
- 모바일 위젯 테스트: 5개 통과
- 모바일 정적 분석: 547개 이슈로 실패. 다수는 Flutter SDK 기본 타입을 인식하지 못하는 형태여서 도구·패키지 경로 문제 가능성이 있으나, 현재 CI 기준으로는 해소가 필요하다.

## 구현에서 확인된 주요 간극

- 웹에서 API를 호출하는 사용 코드가 없다. API 주소 설정은 존재하지만 코치 화면은 프리뷰 데이터에 직접 의존한다.
- 일정 CRUD와 훈련 템플릿은 브라우저 로컬 저장소에만 저장된다.
- 데이터베이스에 공식 스쿼드, 소속 이력, 운영 그룹, 일정 대상 규칙, 세션 실제 참가자, 공지·읽음 상태 모델이 없다.
- API는 경기·마이크로사이클·훈련 세션·블록, 스태프 검토, 선수 목표·이슈, 퍼포먼스 가져오기, 공개본, 변경 이력의 기반을 제공한다.
- 공지, 팀 설정, 권한 관리, 경기 기록, 다수 피드백 동작은 화면 상태만 바꾸거나 정적인 버튼이다.
- 모바일은 역할별 프리뷰 데이터 중심이며 코치 화면에도 동작이 없는 버튼이 다수 있다.

## 해석 원칙

이 검토는 코드·문서·로컬 화면에 근거한 제품 감사다. 실제 지도자 인터뷰, 파일럿 사용 로그, 운영 시간 측정은 아직 없으므로 사용성·시장 적합성에 대한 결론은 가설로 취급한다.
